总览

AI Dev Companion 是一个 TypeScript 单体仓库（monorepo），由 12 个包组成。它能够在 函数这一级别的粒度上追踪代码的每一次改动；除此之外，它还自带一套定制的『规划与执行』 工作流（也就是一组 Claude Code 命令／技能），而这个仓库本身就是用这套工作流来开发的。 整个 DAG（有向无环图）自下而上展开：从最底层的共享类型定义出发，向上经过变更追踪核心、 大模型（LLM）与执行（exec）两大引擎、接好线的各个命令，最后抵达三个最终交付的终点： 一条真正能运转起来的命令工作流、一个可用的 dashboard（网页界面），以及一套可以安装到 其它仓库里的分发机制。

FEAT-aic-01 · 共享类型 (@aidev/types) 已完成

是什么
这是所有包共用的『接口词汇表』，定义了变更分析、模块化、历史记录以及 ECL 相关的各种类型。
为什么做
其它每一个包都要用到这些类型；如果没有一份统一的契约，各个包对同一个概念的理解就会逐渐走样、彼此对不上。
如何做
代码位于 packages/types/src，是一个只含接口定义、不含任何运行逻辑的纯类型包，例如 FunctionAnalysis、ProjectIndex、ChangeRecord 等接口。
为什么这样做
把一个零依赖的类型包放在整张依赖图的最底层，可以让所有包都引用同一份契约，又不会引入循环依赖。
期望结果
所有包都引入 @aidev/types，并以这唯一一份事实来源为准做类型检查。

FEAT-aic-02 · 语法解析与函数身份 (@aidev/ast) 已完成

是什么
面向 Python 和 TypeScript 的 tree-sitter WASM 解析器，负责从代码中提取出函数，并为每个函数计算一个稳定不变的身份哈希。
为什么做
要在函数这一级别追踪代码，就必须给每个函数一个稳定的标识符——这个标识符不能因为代码行号上下挪动就发生变化。
如何做
由几个文件协作完成：wasm-resolver.ts 负责定位 WASM 文件路径，parser-factory.ts 负责创建解析器，parser.ts／ts-parser.ts 分别处理 Python 与 TypeScript，multi-lang.ts 通过 parseFileAuto 按文件扩展名分发。函数身份的算法是 sha256(文件路径+类名+函数名+参数类型)[0:16]。
为什么这样做
用代码结构（而不是行号）来计算身份，函数即使被反复编辑、位置挪动，它的历史记录也能连贯保留；采用 WASM 解析器则免去了本地编译原生模块的麻烦。
期望结果
parseFileAuto 能从 .py／.ts 文件中提取出函数；同一个函数即使在文件里被上下移动，也会算出完全相同的哈希值。

FEAT-aic-03 · 变更追踪核心 (@aidev/core) 已完成

是什么
这是整个产品的核心，集成了一整套能力：解析 diff、给变更打上注释、做变更分析（既有启发式规则，也有大模型分析）、计算模块化指标，以及生成测试。
为什么做
它是整个产品的心脏：要搞清楚到底是哪些函数被改了、为什么改、以及这些改动需要配上什么样的测试。
如何做
按子系统分文件夹：diff/ 负责解析统一格式的 diff 并与 git 集成，analysis/ 负责按函数粒度做分析（含批量处理），modularity/ 负责衡量内聚与耦合并生成契约，test-gen/ 负责为 Python 和 TypeScript 生成测试骨架。
为什么这样做
把 diff、分析、模块化、测试生成各自拆成独立的子系统文件夹，它们就能在共用同一个 ast 层的同时，各自被单独测试、互不牵连。
期望结果
给定一个 git diff，系统能把它解析成带注释的、函数级别的变更清单，并附带自动生成的测试骨架。

FEAT-aic-04 · 历史存储 (@aidev/history) 已完成

是什么
一个用纯 JSON 文件来存储数据的存储层，分别保存评审记录（reviews/）、历史记录（history/）和索引文件（index.json）。
为什么做
为了能够随时间推移追踪代码变更，又不想引入任何数据库依赖。
如何做
代码位于 packages/history/src，把数据以 JSON 文件的形式存放在 .devcompanion/ 目录下；其中 ProjectIndex 带有一份 function_index（函数索引）。
为什么这样做
采用纯 JSON、不依赖数据库，可以让这个 companion 直接塞进任何仓库就能用，而且存下来的内容人可以直接打开查看。
期望结果
变更记录能被持久化保存、之后又能重新加载回来；index.json 把函数的哈希值映射到它对应的历史记录。

FEAT-aic-05 · HTML 报告渲染 (@aidev/render) 已完成

是什么
把带注释的内容渲染成 HTML 报告，包含两种视图：单次会话视图（session view）和代码库 onboarding 视图（onboard view）。
为什么做
让追踪到的代码变更，以及对代码库做的 onboarding 分析，能以人能读懂的方式呈现出来。
如何做
renderSessionToHtml 按『改动原因』把变更分组，并内嵌对应的 diff；renderOnboardHtml 则渲染模块、函数和整体概览。
为什么这样做
在服务端直接渲染出静态 HTML，既不需要任何前端构建步骤，生成的文件又可以在任何地方直接打开。
期望结果
一个 ReviewSession 或 ProjectIndex 能被渲染成一个自包含的、单独的 HTML 文件。

FEAT-aic-06 · aidev 命令行工具 (@aidev/cli) 已完成

是什么
一个基于 Commander 的命令行工具 `aidev`，提供 init、review、render、history、onboard、analyze、idea 等子命令。
为什么做
提供一个由人手动触发追踪和报告的入口，独立于自动触发的 hook 之外。
如何做
调用方式是 packages/cli/dist/main.js <子命令> -p <项目路径>；它把 core、history、render 三个包封装起来供使用。
为什么这样做
命令行工具提供了一种『由用户主动触发』的方式，与自动触发的 hook 并存，而两者共用同一套核心。
期望结果
执行 `aidev <子命令> -p <路径>` 就能针对某个目标项目运行对应的子命令。

FEAT-aic-07 · PostToolUse 钩子 (@aidev/hook) 已完成

是什么
一个 Claude Code 的 PostToolUse 处理器（必须在 100 毫秒内完成），负责在每次编辑动作之后把改动记录到函数级别。
为什么做
用来自动捕获：AI 的每一次编辑都会变成一条带有『改动原因』的可追踪事件，全程不需要人手动登记。
如何做
代码位于 packages/hook/src，对 .py／.ts 文件精确记录到函数级别，对不支持解析的扩展名（如 .yaml／.md）则退化为文件级别记录；记录下来的事件被排队写入 .devcompanion/queue/events.jsonl。
为什么这样做
对不支持的文件采取『退化而不是丢弃』的做法，可以保留一份完整、不缺漏的审计记录；而 100 毫秒的上限则保证编辑器始终流畅、不卡顿。
期望结果
对一个 .py／.ts／.yaml／.md 文件做一次编辑，队列里就恰好多出一条对应的事件。

FEAT-aic-08 · 后台常驻进程 (@aidev/daemon) 已完成

是什么
一个后台常驻进程，从队列里取出事件，异步地完成耗时的 diff 计算与存储工作。
为什么做
把繁重的 diff、分析、存储等工作挪到关键路径之外延后处理，从而让 hook 始终保持快速。
如何做
代码位于 packages/daemon/src，负责把事件队列里的事件逐条取出，并异步地运行 hook 那部分真正耗时的处理逻辑。
为什么这样做
把『捕获』（由 hook 完成）和『处理』（由 daemon 完成）拆开，可以让同步执行的 hook 始终守在它的延迟预算之内。
期望结果
排在队列里的事件会被处理进历史记录，整个过程不会阻塞、拖慢编辑动作。

FEAT-aic-09 · Claude 命令行封装 (@aidev/llm) 已完成

是什么
对 Claude 命令行的一层薄封装，主要提供 callClaude 和 preflight 两个能力。
为什么做
把所有调用大模型的逻辑收拢到同一个地方，这样变更分析、onboarding、idea 这些功能就不必各自重复造一遍。
如何做
代码位于 packages/llm/src，是一个独立的包；它负责拉起 Claude 命令行进程，并处理调用前的环境检查（preflight）。
为什么这样做
选择封装命令行（而不是某个 SDK），既可以直接复用用户本机已有的 Claude 登录凭据，又能把额外依赖压到最少。
期望结果
callClaude 能返回模型的输出；当 Claude 命令行不可用时，preflight 会立刻失败、尽早报错。

FEAT-aic-11 · ECL FN-DAG 执行器 (@aidev/exec) 已完成

是什么
这是 /ccedit 背后的执行引擎：解析 ECL 的 FN 层 DAG、做拓扑排序、找出当前可以开跑的节点、运行验证、再把状态写回去。
为什么做
把一份已经批准的计划（ECL），变成一次按依赖顺序、可以并行的真实执行。
如何做
由若干能力组成：parseEclDag（解析）、validateFnFields（字段校验）、topologicalSort（用 Kahn 算法把图排成 ExecutionLayer[] 一层层）、getReadyNodes（找出可执行节点）、runVerification（运行验证）、updateFnStatus（更新状态）；命令行提供 parse、state、set-status、verify 等子命令。runVerification 里还带有针对 Win32 的进程拉起回退处理。
为什么这样做
这个执行器只依赖 `yaml` 这一个库，因此可以独立、可复用地使用；而拓扑排序分出来的每一层，正好把可以并行的独立节点暴露出来，交给多个并行的子智能体（subagent）去跑。
期望结果
一份带有 functions: DAG 的 ECL，能被成功解析、排成一层层，并报告出哪些节点已就绪、哪些被阻塞。

FEAT-aic-10 · Onboarding 流水线 (scripts/lib) 已完成

是什么
一条完整的流水线，依次是：探测项目类型 → 用 AST 扫描代码 → 用大模型分析每个函数 → 推断出语义层面的 ECL → 生成测试骨架 → 生成概览 HTML。
为什么做
这是 /cconboard 以及 /ccplan 第 10 阶段背后的引擎，用来端到端地读懂一个已有的代码库。
如何做
入口 run-onboarding.ts 调用 onboarding-pipeline.ts 来编排全过程；其中 enhanced-analyzer.ts 负责逐个函数分析其 why／what／how，opus-ecl-generator.ts 负责生成 feature 层的 ECL，ecl-inferrer.ts 负责推断。最终产出 .devcompanion/analysis.json 以及 docs/ecl/<项目名>-features.yaml。
为什么这样做
采用 Opus→Haiku→Opus 的分级策略：用便宜的 Haiku 做逐函数分析以控制成本，而在首尾两端用更强的 Opus 来做整体理解与综合归纳。
期望结果
对一个仓库运行它，就能产出 analysis.json、一份 feature 级别的 ECL，以及一批测试骨架。

FEAT-aic-15 · /ccdiscuss 命令（最小可用版本） 已完成

是什么
一个在正式规划之前先做的、尽力而为的六步对齐循环：先由人写下自己期望的结果，然后 AI 抛出『五个问题』并标出双方理解出现分歧的地方，最终产出一份对齐好的 ECL。
为什么做

FEAT-aic-02 · 语法解析与函数身份 (@aidev/ast) 已完成

是什么
面向 Python 和 TypeScript 的 tree-sitter WASM 解析器，负责从代码中提取出函数，并为每个函数计算一个稳定不变的身份哈希。
为什么做
要在函数这一级别追踪代码，就必须给每个函数一个稳定的标识符——这个标识符不能因为代码行号上下挪动就发生变化。
如何做
由几个文件协作完成：wasm-resolver.ts 负责定位 WASM 文件路径，parser-factory.ts 负责创建解析器，parser.ts／ts-parser.ts 分别处理 Python 与 TypeScript，multi-lang.ts 通过 parseFileAuto 按文件扩展名分发。函数身份的算法是 sha256(文件路径+类名+函数名+参数类型)[0:16]。

期望结果
parseFileAuto 能从 .py／.ts 文件中提取出函数；同一个函数即使在文件里被上下移动，也会算出完全相同的哈希值。

捕获层 技能树 · 五问总结

是什么
这是『自动记录』那一层。它由两部分组成：一个在每次编辑动作之后立刻触发的钩子（PostToolUse hook），以及一个在后台慢慢处理这些记录的常驻进程（daemon）。
为什么做
我们希望开发者每改一次代码，这次改动连同『为什么改』都能被自动记下来，而不需要人去手动登记。与此同时，这个记录动作绝对不能拖慢编辑器，让人感觉卡顿。
如何做
钩子在 100 毫秒之内完成工作：Python 和 TypeScript 文件精确记录到函数级别，其它类型的文件则退化为文件级别记录，然后把事件写进一个队列。后台常驻进程再从队列里把事件取出来，做真正耗时的 diff 与分析。
为什么这样做

是什么

FEAT-aic-21 · 安装／更新／查看状态／卸载 生命周期 + 注册表 终点

是什么
把这个 companion 安装到其它仓库里去——整个过程是幂等的，并由一份注册表（registry）追踪。
为什么做
让其它项目能够采用这个 companion（它的各个命令、配置和 hook），而不必靠人手动把文件复制过去。
如何做
命令是 scripts/install.ts <目标路径> [--enforce] [--no-commands]；配套还有 update.ts／status.ts／uninstall.ts；由注册表来追踪每一次安装。目前已经装进了 5 个相邻的仓库。
为什么这样做
正因为它幂等、又有注册表追踪，所以重复运行安装是安全的，而每个目标仓库的更新内容也都能逐个对比（diff）出来。
期望结果
向某个目标仓库安装时，会把命令、配置、hook 都接好；status／update／uninstall 负责后续管理；重复安装则是一个无副作用的空操作。
