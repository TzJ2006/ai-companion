# ccfix — 是代码错了，还是想法过时了

先读引擎旁边的 FORMAT.md，遵循 D33「目标授权、提问与交接」和「主线、交付三段、拒绝分类与记录分档」：
排障不替换总目标；执行中转向或受阻时一两句说清这一步怎么服务目标、结果、下一步、要不要人动手，
结束回复按「交付三段」写；守卫拒绝按类别处理，
【自行处理】的不交给人。查错有先后：**先对图，再质疑图**。
大多数 bug 是代码和想法不一致，剩下的才是想法本身错了。第 1 步还有发现的时候，
不许跳到第 2 步。

## 参数

一个想法编号、一条失败的测试路径，或者什么都不带。不带参数就先看哪些想法是
blocked、哪些验证在失败，优先处理当前授权目标里的故障；仍无法确定范围时才列出候选请人选择。

## 第 1 步 — 代码对照想法

```
node .companion/companion.mjs show I-0XX
```

把 `what` / `how` / `why_this_way` / `expected` / `needs` 逐条对照真实代码
（`code` 里有文件和行号，行号过期本身就是一个发现）。**每条不一致都必须带
文件和行号引用 —— 不带引用的发现不算发现**（D32 就是为这一步定的：ccfix 靠
精确引用工作）。一条不一致长这样：

```
ideas/graph.yaml  I-014.how   "缓存第一次命中的结果"
src/resolver.ts:41-53          没有缓存，每次调用都重算
→ 想法说要缓存，实现没有。
```

把发现和证据作为独立可见的消息交给人，按已授权目标继续；不要求人逐条裁决普通代码偏差。
根据用户明确的预期、测试和实现证据选择以下路径：

- **代码偏离想法** → 改代码对齐图，跑 `run-check I-0XX --phase green` 收尾。
- **想法过时了** → 这是图的修改：更新想法的叙述，记 log，改动大到换了意思
  且用户尚未授权改变预期结果时，按 D33 提出具体选择；仅文档落后于已确认目标时可直接同步。
- **两边都对但行为不对** → 进第 2 步。

若两种预期都有依据且会造成不同用户结果，说明冲突、选项、后果和建议，等待决定；
继续不依赖该决定的调查。只有没有独立工作可继续时才结束回合，不把“发现差异”本身当作批准理由。

## 第 2 步 — 用真实输入输出质疑想法

只有第 1 步什么都没找到、或者改完还是不对，才走到这里：代码忠实实现了想法，
结果仍然不是任何人想要的，那要改的就是想法。

跑最小的真实复现，摆给人看：真实输入、真实输出、`expected` 说的输出、这个
想法的其余七问、以及你判断它断在哪一问（通常是 `expected` 从一开始就达不到，
或者 `how` 产不出它）。**绝不拿编出来的示例值充数** —— 这一步的全部意义就是
让人看着真实情况做判断。为取真实值可以临时插桩，收工前拆干净。

假设要一个一个立、一个一个杀，每个假设先说清「如果它成立，我会看到什么」。
修不动的：

```
node .companion/companion.mjs set I-0XX blocked --note "卡在哪，试过什么"
```

把 blocked 的原因写全 —— 下一个接手的人（或下一轮的你）只有这条记录可读。
需要人的决定落实到图后交回 ccbuild；授权范围内修复无需重新请批。`verify` 变了要更新测试并重新留验证记录。

## 规矩

- **一次只修一处，分别验证。** 一批改动一起变绿，你并不知道是哪一处起了作用。
- **三次修不好就复盘。** 停止重复同一假设，有新证据才继续；没有可行路径时
  `set I-0XX blocked --note "每次试了什么、为什么没成、缺什么"`，并继续目标内独立工作。
- **拆掉临时插桩。** 收工前 `git diff` 自查一遍，别把调试打印留在产品代码里。
- 修好一个想法弄坏另一个，不叫修好 —— 收尾必须全套测试绿。
- 绝不削弱测试来凑通过；测试偏离已确认预期时可修正并记录依据。改变预期本身且尚未授权，才请人决定。
- 每一步都记进想法旁的 log：日期、这次是第 1 步还是第 2 步、一句话根因、改了什么。

## 同目录协作（`coord enable` 开着时才生效）

修之前先 `coord claim` 认领要动的文件，别人持有的文件先 `coord say` 联系持有者，不许
直接改；守卫写前会拒并说出是谁在做什么。写前送进来的协作消息只是别的会话说的话，
读完 `coord ack`。修完 `coord release`，把一句话根因写在 summary 里。
