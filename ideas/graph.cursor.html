八问的想法节点格式 进行中I-001

这个想法是什么
一个想法节点的格式：八个必答问题（是什么／为什么有这个想法／预期结果／如何实现／ 为什么这样实现／代码在哪个文件的哪几行／如何验证／未来怎么用），加上一种边 needs 表示前置。一种节点、一种边，全部放在一个 YAML 文件里。
为什么有这个想法
AI 会产生幻觉、一句 prompt 对不齐真实需求、返工之后连自己都看不懂项目框架 —— 这三件事的根因是同一个：想法从来没有被写下来，只有代码被写下来了。
预期结果是什么
任何一个想法，人和 AI 读同一份记录得到同一个理解；一个没有上下文的 agent 冷启动读这个文件就能接着干。
要如何实现
YAML，一个扁平的 ideas 列表。规格写在 claude-companion/FORMAT.md，问题 1-5、7、8 在写代码之前回答，问题 6 回答两次（计划时写 file/symbol，实现后补 lines）。
为什么要这样实现
选一层扁平结构而不是需求／特性／模块／函数四层 —— README 里写明了理由：四层结构 本身就是「看不懂项目框架」的那种复杂度，而人的心智模型是「所有想法都变成一个个模块」， 模块不是分类法。用 YAML 而不是 JSON，因为八个回答都是成段散文，JSON 写多行散文没法读。

图的解析与校验 已完成I-002

这个想法是什么
读 graph.yaml 并检查它没有烂掉：id 唯一、needs 指向存在的想法、图无环、 done 的节点必须有 code 和 verify、code 指的文件真的存在、人工验证必须有人签字； 八问里没填的字段作为警告列出来。
为什么有这个想法
没有校验，图会安静地烂掉：done 却没有代码、code 指向已经删掉的文件、两个想法互相依赖。 烂掉的图比没有图更糟，因为它看起来是完整的。
预期结果是什么
健康的图 check 通过、退出码 0；每一种烂法都被指出来并说明是哪个 id； 未回答的八问以 warning 出现，不阻塞。
要如何实现
DFS 三色标记查环（findCycle）；从 endpoints 沿 needs 反向遍历找出不通向任何终点的 想法（orphans）；existsSync 验证 done 节点的 code 路径。
为什么要这样实现
把「done 必须有 code + verify」做成硬错误而不是警告 —— 这是整套东西成立的前提： 如果「完成」可以没有证据，这张图就只是一份愿望清单。反过来，八问没填只做警告， 因为机器判不了回答的质量，硬拦一个判不准的东西比不拦更糟。

这个想法是什么
改一个想法的状态，同时在它自己的 log 里追加一条；写回时保留 YAML 注释； 拒绝没有 code / verify 的 done，拒绝没签字的人工验证。

改了什么代码、什么文档、什么想法要有详细记录，而且原因要放在想法旁边而不是 另一个文件里 —— 放远了就没人读。
预期结果是什么

这个想法是什么

强制层：七条 hook 规则 进行中I-007

这个想法是什么
七条跑在 harness 层、agent 绕不过去的规则：R1 每次编辑自动记录；R2 已有想法的 status 只能通过 set 改；R3 测试文件不存在就不准写实现；R4 how／why_this_way 没填就不准动它的代码；R5 图有错误就不准结束回合；R6 没有人批准过的图不准开始实现； R7 扫描清单只能被真实 Read 划掉。
为什么有这个想法
五条命令都只是 prompt —— agent 可以跳过调研、编造 why_this_way、直接用 Edit 把 status 改成 done 绕过所有校验。写在提示词里的纪律，到了第三十轮对话就不算数了。
预期结果是什么
跳过测试写实现会被拒绝并告诉它先写哪个文件；手改 status 会被拒绝并给出该跑的 set 命令；没人批准过的图上动手会被拒绝；每次编辑都在 ideas/log.md 里留一行。
要如何实现
一个 guard.ts 挂在 PreToolUse / PostToolUse / Stop / UserPromptSubmit 四个事件上， 按 hook_event_name 分派；退出码 2 + stderr 表示「拦下并把原因告诉 Claude」。 批准绑定在图的 sha256 前 12 位上，改一个字就失效。
为什么要这样实现
只强制机器判得了的事：文件存不存在、字段填没填、状态变没变、check 过不过、 人有没有亲口批准。批准挂在 UserPromptSubmit 上，因为那是唯一 agent 造不出来的事件； 判定要求整条消息就是「批准」，否则「我不批准」会被算成批准。 所有异常路径一律 fail open —— 守卫自己崩了不能把人锁在外面。

/ccscan — 通读项目建图 进行中I-008

这个想法是什么
读完整个项目的每个文件、每份文档、每行代码和注释，问人终点是什么， 抽出所有想法连成图，渲染出来，并诚实报告读了多少、跳过了什么、哪些问题没答上。
为什么有这个想法
接手一个自己已经记不住的项目时，第一件事是重新看清它的形状。
预期结果是什么
跑完得到一张图，加上一份诚实的清单：读了多少文件、跳过了哪些、 哪些节点的 why_this_way 或 verify 没能找到答案。
要如何实现
按「意图 → 结构 → 代码 → 历史」的顺序读；用 AskUserQuestion 问终点； 从代码结构、注释、commit message 和设计文档里抽想法；找不到理由就写 null 并列进报告。
为什么要这样实现
明确禁止编造 why_this_way —— 编出来的理由会被下一个 agent 当成事实并且一直 维护下去，这是这条命令能造成的最大伤害。所以宁可留空并列进报告，让下一次 /ccthink 去补。

/ccthink — 对齐、拆分、调研、排期 进行中I-009

这个想法是什么

函数级变更追踪核心 已完成I-014

这个想法是什么
把一次 git diff 解析成「哪些函数改了、改了什么、为什么改」：tree-sitter 解析 Python/TypeScript 出函数，给每个函数算一个不随行号变动的身份哈希，把 diff hunk 归因到函数，存成 JSON 历史，再渲染成自包含 HTML 报告。
为什么有这个想法
在 git blame 的「谁改了什么」之上，补上「为什么改」和「改了哪个函数」这一层语义。
预期结果是什么
给定一个 git diff，得到函数级别的变更清单并存进历史；同一个函数在文件里上下移动， 算出来的哈希完全相同。
要如何实现
六个包单向串成一条链：types（只有接口）→ ast（wasm-resolver 定位 .wasm、 parseFileAuto 按扩展名分发、identity 算哈希）→ core（diff 解析 + annotateChanges 归因）→ history（JSON 存储 + index.json）→ render（HTML）→ cli（aidev 八条子命令）。 身份 = sha256(文件路径::类名::函数名::参数 name:type)[0:16]。
为什么要这样实现
用代码结构而不是行号算身份，函数被反复编辑、挪动位置，历史仍然连贯； 用 WASM 解析器免去本地编译原生模块；存 JSON 不依赖数据库，因为这个 companion 要能直接塞进任何仓库，而且存下来的东西人可以直接打开看。 （理由取自 docs/ecl/dag/ai-companion.ecl.yaml 的 Foundation 层记录。）
