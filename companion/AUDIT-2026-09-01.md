# AI Dev Companion 共同层 V2 审计

- 审计日期：2026-09-01
- 审计范围：`companion/` 共同层、Claude/Cursor/Codex Hook 接入、ideas graph、安装与迁移流程、共享 skills 与测试
- 审计性质：只读架构与实现审计；本文不代表问题已修复
- 目标：在不影响当前版本的前提下，新增一套可由 Claude Code、Codex 和 Cursor 共用的 Companion V2，并通过各平台 Hook 接入同一共同层

## 结论

整体方向正确：保留一个 ideas graph、一个 TypeScript 核心、一个可分发 bundle，以及 Claude/Cursor/Codex 三个很薄的输入输出适配层，是值得继续推进的方案。当前共享层的 12 个测试文件、115 个测试已经通过，说明核心结构具备可用基础。

但当前版本**不建议直接激活真实 Hook**。主要原因不是缺少功能，而是尚未真正实现“与现有版本并存、可安全切换、失败可回滚”，并且图状态、签字和 RED gate 仍存在可绕过路径。若现在安装，可能同时运行旧 Hook 与新 Hook，也可能在安装中途留下部分配置。

建议发布判定：**暂缓激活（NO-GO），允许继续开发和隔离验证。**

## 已做得好的部分

1. `ideas/graph.yaml` 作为单一事实来源，避免为三个客户端维护三套状态。
2. 核心逻辑集中在 `companion/*.ts`，构建成单文件 bundle，分发模型清晰。
3. Claude、Cursor、Codex 使用小型 normalizer/encoder，而不是建立复杂 adapter 类层级。
4. 审批与内容摘要绑定，RED/GREEN、migration、receipt 等关键概念已经进入设计。
5. 五个共享 skill 可以作为跨客户端的一致操作界面。
6. `FORMAT.md` 已记录大量明确的设计决策，后续可据此做一致性测试。

## 阻断项

### P0-1：V2 尚未与当前版本真正隔离

**证据**

- `companion/install.ts` 会直接复制 bundle 和 skills，并修改 `.claude/settings.json`、`.cursor/hooks.json`、`.codex/hooks.json`。
- 安装过程会直接创建 `ideas/graph.yaml`，随后才做 smoke check；中途失败可能留下半安装状态。
- 读取无效 JSON 时存在回退为空对象并重新写入的路径，可能覆盖用户原有配置。
- 如果先创建空 graph，旧数据迁移可能因为目标 graph 已存在而被阻断。
- 现有 Hook 没有被明确停用。Codex 官方 Hook 语义是：来自多个配置来源且匹配同一事件的 Hook 都会运行；同一事件的多个 command Hook 可并发运行。因此，“写入新配置”不等于“替换旧版本”。

**影响**

- 无法保证“不影响当前情况”。
- 新旧 Hook 可能重复执行、重复阻断或产生不一致状态。
- 安装失败后缺少可靠恢复路径。

**建议**

- 源码仍保持一个 `companion/`，但安装产物使用中立、带版本的路径，例如 `.aidev-companion/v2/companion.mjs`。
- 将安装拆成以下动作：
  1. `install --stage`：只复制 V2 产物并验证，不写活动 Hook。
  2. `migrate --dry-run`：显示将迁移的数据、冲突与遗漏。
  3. `activate --platform claude|cursor|codex`：逐个平台启用。
  4. `deactivate` / `rollback`：恢复激活前配置。
- 每次修改配置前保存精确备份，并以事务方式写入：全部验证成功后再替换活动配置。
- 新版本开发建议放在独立分支或 worktree，例如 `codex/companion-v2`；运行时数据与当前版本也必须使用独立命名空间。

### P0-2：graph 状态与签字约束可被绕过

**证据**

- `companion/guard.ts` 的 `ruleGraphEdit()` 在事件没有标准化 `edit` 内容时直接放行。Codex 的 `apply_patch` 事件可能只有 patch operations，没有完整 edit 对象，因此对 `status`、`signed_off` 等受保护字段的修改可能绕过规则。
- `companion/ideas.ts` 的 `applyChanges()` 接受任意 `set.field`，并支持直接 `sign`，与“签字只能由真实用户提交并与内容绑定”的设计目标冲突。
- `todo -> doing` 尚未完整强制“已拆解 + 当前计划已审批”。已有 decomposition approval 没有形成可靠的消费链路。

**影响**

- Agent 可能通过通用变更接口直接修改受保护字段。
- graph 中的签字无法证明来自当前用户、当前内容和当前审批动作。
- 工作项可能绕过计划审批进入执行状态。

**建议**

- 为 `set.field` 建立最小白名单；明确禁止直接写入 `status`、`signed_off`、审批摘要和系统维护字段。
- 删除通用 `sign` 变更。Web/UI 只能创建“等待人工确认”的请求；真正签字仅由可信的用户提交事件完成。
- Codex `apply_patch` 必须解析 patch operations，或在无法可靠判断目标字段时 fail closed。
- 把 `todo -> doing` 写成一个原子状态转换，统一验证拆解、计划摘要、用户审批与内容摘要。
- 为所有受保护字段增加三平台一致性测试和绕过测试。

### P0-3：检查命令失败会被误判为 RED

**证据**

- `runCheck` 通过 shell 执行可编辑命令；非零退出、命令不存在、超时或被信号终止都可能被统一解释为 RED。
- 执行当前验证命令前，没有可靠证明该命令本身已经随当前计划被用户审批。

**影响**

- “验证基础设施坏了”可能被误判为“测试发现真实失败”，从而错误打开 RED gate。
- Agent 可能修改验证命令来制造可编辑范围或扩大操作权限。

**建议**

- 将结果至少拆分为 `GREEN`、`RED`、`INFRA_ERROR`、`TIMEOUT`、`CANCELLED`。
- 只有测试进程正常启动并返回被认可的失败语义时，才生成 RED。
- 验证命令、工作目录、允许的环境变量和超时必须绑定到当前已审批计划摘要。
- 默认避免 `shell: true`；优先使用明确的 executable 与 argv。

## 高优先级问题

### P1-1：并发写入仍可能丢失更新

**证据**

- graph 保存使用临时文件与 rename，能降低文件损坏风险，但缺少“读取时摘要/版本”和“提交前重新检查”。
- 两个 Agent 同时读取同一版本后写入，后写者仍可能覆盖先写者。
- runtime、receipt、apply 相关输出并非全部使用相同的原子写入协议。

**建议**

- graph 增加单调递增 revision 或内容 digest。
- 每次变更携带 `expected_revision`；保存前重新读取，冲突时拒绝并要求重新计算。
- graph、runtime、receipt 和 apply 结果统一采用临时文件、flush、原子替换与冲突检查。
- 增加双进程/双 Agent 并发测试。

### P1-2：Hook 路径、SessionStart 和输出协议不完整

**证据**

- Cursor/Codex 配置使用相对路径 `.claude/companion/companion.mjs`。当会话从仓库子目录启动时，路径可能失效。
- Codex 官方文档建议仓库内 Hook 从 Git root 解析。
- 配置声明了 `SessionStart`，但当前 normalizer/entry 没有提供明确的状态简报行为。
- Cursor 的 prompt 输出存在普通文本与 JSON 拼接的风险，可能破坏宿主协议。
- installer smoke test 直接调用 bundle，没有验证真实配置发现、信任确认、工作目录和宿主传输格式。

**建议**

- 统一使用 Git root 解析脚本，再定位中立的 V2 安装路径。
- 为 `SessionStart` 明确定义一个稳定、短小、只读的 briefing schema。
- 每个平台每次 Hook 调用只输出一种合法协议；日志写入 stderr 或独立日志文件。
- 增加从仓库根目录、一级子目录和深层子目录启动的真实宿主测试。
- 对非 managed/plugin Hook 的 trust/review 流程给出明确安装提示。

参考：[Codex Hooks 官方文档](https://developers.openai.com/codex/hooks)

### P1-3：规范 D30-D32 与实现仍有缺口

**证据**

- `check()` 尚未完整强制当前 GREEN/manual receipt 的有效性。
- 行号边界、路径安全和有限 glob 约束没有全部落到统一验证函数。
- migration 没有完整迁移审批与证据，和 graph 中对迁移节点的描述不完全一致。
- 被跳过文件缺少结构化 reason，难以审计为什么没有处理。

**建议**

- 将 D30-D32 转成表驱动 conformance tests，不再只依靠文档约定。
- 所有 receipt 必须绑定 graph revision、计划摘要、命令摘要、输入文件摘要和时间范围。
- 对每个 skipped file 保存固定枚举 reason 与可选详情。
- migration 输出逐项映射报告：已迁移、无法迁移、需人工确认、被拒绝。

### P1-4：共同层仍带有 Claude 专属路径

**证据**

- 共享 skills 中仍硬编码 `.claude/companion/companion.mjs`。
- 仓库根目录有 `CLAUDE.md`，但没有等价的中立入口说明；Codex/Cursor 的操作约束可能依赖各自隐式配置。

**建议**

- 所有共享 skill 调用中立 launcher，例如 `.aidev-companion/v2/bin/companion`。
- 平台目录只保留薄适配与注册配置，不承载共同业务规则。
- 增加一份中立的仓库级说明，并让 Claude/Cursor/Codex 的入口文件引用同一份规则。

## 建议的最小目标架构

```text
repository
├─ companion/                    # 唯一源码与规范
├─ ideas/graph.yaml              # 唯一项目状态
├─ .aidev-companion/
│  └─ v2/
│     ├─ companion.mjs           # 版本化共同运行层
│     ├─ manifest.json           # 版本、摘要、兼容范围
│     ├─ runtime/                # V2 独立运行数据
│     └─ backups/                # 激活前配置备份
├─ .claude/                      # Claude 薄接入
├─ .cursor/                      # Cursor 薄接入
└─ .codex/                       # Codex 薄接入
```

共同层负责：graph 规则、审批摘要、RED/GREEN、receipt、并发控制、迁移和公共命令。

平台层只负责：事件标准化、调用共同层、将统一结果编码为宿主要求的格式。

## 整改顺序

1. **先做隔离**：版本化路径、stage、backup、activate、deactivate、rollback。
2. **关闭安全绕过**：保护 graph 字段、取消直接 sign、修复 patch 解析、原子状态转换。
3. **修复 RED 语义**：区分测试失败和基础设施失败，并绑定已审批命令。
4. **增加并发控制**：revision/digest compare-and-swap，覆盖所有状态文件。
5. **完成规范一致性**：把 D30-D32、migration、skip reasons 转为自动测试。
6. **最后接真实宿主**：依次验证 Claude、Cursor、Codex，再逐个平台激活。

## 激活前验收门槛

只有以下条件全部满足，才建议从 stage 进入 activate：

- [ ] 安装 V2 不修改任何现有活动 Hook。
- [ ] 三个平台都能独立 activate/deactivate，并能一键 rollback。
- [ ] 安装任一步失败后，活动配置与安装前逐字节一致。
- [ ] 旧 Hook 与 V2 Hook 不会同时匹配并运行，除非显式选择兼容模式。
- [ ] graph 受保护字段无法通过 `apply_patch`、通用 `set`、Web 请求或平台差异绕过。
- [ ] 签字只能来自真实用户事件，并绑定当前内容摘要与 graph revision。
- [ ] `todo -> doing` 必须消费当前有效的拆解与计划审批。
- [ ] RED 不会由命令缺失、超时、取消或启动失败产生。
- [ ] 两个并发 Agent 不会静默覆盖彼此的 graph 更新。
- [ ] 从仓库任意子目录启动时，三平台 Hook 都能定位共同层。
- [ ] D30-D32 的每条规则都有正向、反向和绕过测试。
- [ ] migration dry-run 能完整报告审批、证据、冲突与跳过原因。
- [ ] 在真实 Claude、Cursor、Codex 会话中完成端到端测试，而不仅是直接调用 bundle。

## 建议补充的测试

1. 无效宿主 JSON 配置不得被覆盖。
2. stage 失败、activate 失败、smoke 失败的逐阶段回滚。
3. 新旧 Hook 同时存在时的检测与拒绝。
4. Codex `apply_patch` 修改 `status` / `signed_off` 的绕过测试。
5. `set.field` 任意字段注入与 direct sign 拒绝测试。
6. 命令不存在、超时、被取消、进程崩溃不得生成 RED。
7. 两个进程基于相同 revision 同时写 graph，只允许一个成功。
8. 从根目录、子目录、worktree 启动的路径解析测试。
9. SessionStart 输出协议快照测试。
10. Claude/Cursor/Codex 对同一输入产生等价共同层决策的契约测试。

## 最终建议

不要再复制三套 Companion 业务逻辑。继续维持“一个共同核心 + 三个薄平台接入”，但先把共同层当成一个可版本化、可 staged、可回滚的本地产品来建设。

V2 的第一个里程碑不应是“更多 Hook 能力”，而应是：**它可以完整安装、验证和卸载，同时当前版本完全不受影响。** 在这个基础上关闭 graph、签字和 RED gate 的绕过路径，再做真实三平台激活，风险最低。
