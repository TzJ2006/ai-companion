# ccapply — 图改了，代码跟上

先读引擎旁边的 FORMAT.md，遵循 D33「目标授权、提问与交接」和「主线、交付三段、拒绝分类与记录分档」。这条工作流的范围
**只有本次改动触到的想法**；全图对齐是 ccfix 的事，一次提交不该引发全仓库漫游。

## 参数

一个改动文件的路径就只写回那一份；一个想法编号就只对齐那一个（跳过找文件那一步，
直接进第 3 步）。不带参数：在 `ideas/` 里找本次的改动文件，写回，然后对齐它触到的想法。

## 第 0 步 — 现在这张图是哪一版

```
node .companion/companion.mjs check
node .companion/companion.mjs paths
```

`check` 不过不许写回。`paths` 打印的图路径是唯一的图，不许猜文件名。

## 第 1 步 — 找改动文件

网页上点「提交」时，有本地服务（`serve`）就已经直接写回了，这一步为空；
没有本地服务时，改动文件落在下载目录，人要先把它移到 `ideas/` 下。

在 `ideas/` 里找 `*.json` 里 `baseDigest` 等于当前图指纹的那一份。指纹不等的逐个
报出来（写成于哪一版、现在是哪一版）并忽略，**不许**替人猜它还想不想要。一个都
找不到时提醒：「检查是否存进了下载目录」。

## 第 2 步 — 写回，并把差异交给人看

```
node .companion/companion.mjs apply ideas/那份改动.json
```

`apply` 会拒绝陈旧的、越权的（改 status、签字）、会让图出错的改动，拒绝时改动文件
原样留着。写回成功后，把这几样作为一条独立可见的消息送到人眼前：

1. 逐字段差异：哪个想法、哪个字段、旧值、新值（`apply` 逐条打印了）。
2. `check` 的结果和新指纹。
3. **哪些想法八问没齐、本轮不实现** —— 网页上新建的想法只有前三问，都在这一列；
   它们要先走 ccthink 补齐，不在这里硬写。
4. 本轮要对齐的想法清单：本次改动触到的、八问齐全的那几个。

**不需要口令。** 计划批准这道门 2026-09-16 起已拆（FORMAT.md D7 修订）；人看一眼
说「继续」就继续，说改就回网页改。人不吭声、且清单里没有新建的想法时，可以继续。

## 第 3 步 — 只对清单里的想法对齐代码

对每一个想法，按 ccbuild 的顺序来，一个一个，不并行：

```
node .companion/companion.mjs show I-0XX
node .companion/companion.mjs set I-0XX doing
```

先逐条对照八问和现有代码，列出「想法说的」和「代码做的」不一致的地方（带行号）；
按 `verify.test_files` 补或改测试，让测试断言新的 `expected`；跑 `run-check I-0XX --phase red`
看着它因为「还没改」而失败；再改实现；`run-check I-0XX --phase green` 拿绿；
把真实行号填回 `code.lines`；`set I-0XX done`。

已完成的想法被改了行为字段会被 `apply` 自动退回 blocked（D19），受阻原因写着为什么；
它就是这一步要重新走 doing → done 的对象。

**图里没被改过的部分不许动。** 顺手发现别的问题，记下来交给 ccfix，不在这里修。

## 第 4 步 — 收尾

```
node .companion/companion.mjs check
node .companion/companion.mjs render
```

报告按 D33「交付三段」：完成了什么（写回了几处、对齐了哪几个想法、各自的验证是否通过）、
agent 接着做什么（哪些想法因八问未齐留给 ccthink）、人现在需要做什么——至少这一句固定：
**回浏览器刷新页面**，再做下一轮。

## 分工，写清楚

改一个错别字直接在对话里说更快（改散文字段本来就允许直接用编辑工具做）。这条链路的
价值在批量的散文修改和增删想法、改前后关系这类结构变更 —— 那些在网页上点比在 YAML
里改可靠。
