八问的想法节点 进行中I-001

是什么
一个想法节点的格式：八个必答问题（是什么／为什么／预期结果／如何实现／ 为什么这样实现／代码在哪／如何验证／未来怎么用），加上一条 needs 边表示前置。
为什么有这个想法
AI 会产生幻觉、prompt 对不齐需求、返工之后自己也看不懂项目框架 —— 这三件事 的根因是同一个：想法从来没被写下来，只有代码被写下来了。
预期结果
任何一个想法，人和 AI 读同一份记录，得到同一个理解；一个陌生 agent 冷启动 读这个文件就能接着干，不需要上下文。
如何实现
YAML，一个扁平的 ideas 列表，一种节点、一种边。规格写在 FORMAT.md。
为什么这样实现
选一层扁平结构，而不是需求／特性／模块／函数四层 —— 因为提出的诉求是 "所有想法都变成一个个模块"，模块不是分类法。四层结构本身就是让人看不懂 项目的那种复杂度。YAML 而不是 JSON，因为八个回答都是成段的散文， JSON 里写多行散文没法看。

是什么
读 graph.yaml，检查 id 唯一、needs 都指向存在的想法、图无环、done 的节点 必须有 code 和 verify、code 指的文件真的存在、人工验证必须有人签字。
为什么有这个想法
没有校验，图会安静地烂掉：done 却没有代码、code 指向已经删掉的文件、 两个想法互相依赖。烂掉的图比没有图更糟，因为它看起来是完整的。
预期结果
一个健康的图 check 通过、退出码 0；每一种烂法都能被指出来，并且指出是哪个 id。
如何实现
DFS 三色标记查环；从 endpoints 反向遍历 needs 找出不通向任何终点的想法； existsSync 验证 code 路径。
为什么这样实现
把"done 必须有 code + verify"做成硬错误而不是警告 —— 这条是整套东西成立的 前提：如果"完成"可以没有证据，那这张图就只是一份愿望清单。

状态写回与记录 已完成I-005

是什么
改一个想法的状态，同时在它自己的 log 里追加一条记录；写回时保留 YAML 注释； 拒绝没有 code / verify 的 done，拒绝没签字的人工验证。
为什么有这个想法
改了什么代码、什么文档、什么想法，需要有一份详细的记录。原因要放在想法旁边， 而不是另一个文件里 —— 放远了就没人读。
预期结果

走 Document 而不是 parse → 改 → stringify：后者会把整个文件的注释和排版 全部抹掉，而注释正是人留给自己的东西。

/ccscan — 通读项目建图 进行中I-006

是什么
读完整个项目的每个文件、每份文档、每行代码和注释，抽出所有想法， 连成图，渲染出来。
为什么有这个想法
接手一个自己已经记不住的项目时，第一件事是重新看清它的形状。
预期结果
跑完得到一张图，加上一份诚实的清单：读了多少文件、跳过了哪些、 哪些节点的 why_this_way 或 verify 没能找到答案。
如何实现
按"意图→结构→代码→历史"的顺序读；从代码结构和 git log 里抽想法； 终点问人；找不到理由的地方写 null 并列进报告。

/ccthink — 对齐、拆分、调研、排期 进行中I-007

是什么
三个高层问题对齐 → 拆成小想法 → 渲染出图让人审核 → 调研（仓库内 + 联网， 能借就借）→ 回答如何实现和为什么这样实现 → 设计测试方案 → 按周排出完整计划。
为什么有这个想法
一句 prompt 对不齐需求。返工的成本远高于先花二十分钟对齐的成本。
预期结果
拿到一份可以直接交给别人执行的计划：图审过了、借用的东西列清楚了、 每个节点的测试要断言什么说明白了、按周排好了。
如何实现
六步，顺序固定。第 2 步之后必须停下来等人审图；第 3 步的调研必须在 回答"如何实现"之前完成。
为什么这样实现
"能借就借"设成这个命令里优先级最高的规则：除非人明确禁止某个项目， 只要存在可用的东西就借，自己造需要一个经得起追问的理由。 顺序上把调研放在"如何实现"之前，否则调研只会变成给已有答案找依据。

/ccfix — 先查一致性，再查想法 进行中I-009

是什么
第一步：对照 code 指的行，逐条找出实现和想法不一致的地方，带行号引用， 交人审核后再改。第二步：如果一致，那就是想法本身错了 —— 摆出真实的 输入输出和完整八问，让人来改想法。
为什么有这个想法
大部分 bug 是代码和想法不一致；剩下的是想法本身错了。 跳过第一步直接改想法，会把对的代码改坏。
预期结果
每一条发现都带文件和行号；没有行号的不算发现。
如何实现
读 code 指的每一段，逐项对照 what / how / why_this_way / expected / needs； 列出全部不一致后停下来，一条条问人：是代码错了，还是想法过期了。
为什么这样实现
故意不让 AI 自己判断哪边对 —— 它恰恰是判断不了的那一方， 这就是这一步以人审收尾的原因。第二步要求摆真实值而不是举例值， 因为这一步的全部意义就是让人看见现实。

强制层：七条 hook 规则 已完成I-013

是什么
七条跑在 harness 层、agent 绕不过去的规则：每次编辑自动记录；已有想法的 status 只能通过 set 修改；某个想法的测试文件不存在就不准写它的实现； how / why_this_way 没填就不准动它的代码；图有错误就不准结束回合； 没有人批准过的图不准开始实现；文件只有被真的 Read 过才算扫描过。
为什么有这个想法
前面五个命令都只是 prompt —— agent 可以跳过调研、可以编造 why_this_way、 可以直接用 Edit 把 status 改成 done 绕过所有校验、可以自问自答说"看起来 合理"然后接着往下做、可以只读了主要文件就宣称通读完了。 写在提示词里的纪律，到了第三十轮对话就不算数了。
预期结果
跳过测试直接写实现会被拒绝并告诉它先写哪个文件；手改 status 会被拒绝并 给出该跑的 set 命令；没人批准过的图上动手会被拒绝并要求先给人看； 扫描进度是"已读 487/511"这样的数字而不是一句"我读完了"； 每次编辑都在 ideas/log.md 里留下一行，不需要 agent 配合。
如何实现
一个 guard.ts 挂在 PreToolUse / PostToolUse / Stop / UserPromptSubmit 四个事件上，按 hook_event_name 分派；退出码 2 + stderr 表示"拦下并把原因 告诉 Claude"。批准绑定在图的 sha256 上；扫描清单由 git ls-files -z 生成， 每次 Read 划掉一个。install.ts 负责把它加进目标仓库的 .claude/settings.json，且不覆盖别人的 hook。
为什么这样实现
只强制机器判得了的事：文件存不存在、字段填没填、状态变没变、check 过不过、 人有没有亲口批准、文件有没有真的被读进上下文。 批准挂 UserPromptSubmit、扫描挂 Read，是同一个思路：把"我做了"绑到一个 不真做就产生不了的事件上 —— 任何 agent 写得进去的标记，agent 就能伪造。 判断"整条消息就是批准"而不是"消息里含批准"，否则"我不批准"会被算成批准。 八个回答的质量、联网搜索是否诚实 —— 这些仍然强制不了，唯一的防线是让遗漏 在 check 和渲染里可见。硬拦一个判不准的东西，比不拦更糟。 所有异常路径一律放行（fail open）：守卫自己崩了不能把人锁在外面。

装到其它仓库 进行中I-011

是什么
把五个命令装进任意一个仓库的 .claude/commands/，路径改写成绝对路径， 并建一个空的 ideas/graph.yaml。
为什么有这个想法
这套流程要用到我所有的项目上，不是只用在这一个仓库里。
预期结果
在别的仓库里能直接用这五个斜杠命令；不覆盖已经存在的、不属于这套工具的命令文件。
如何实现
复制 commands/*.md 并把 `claude-companion/` 替换成本目录的绝对路径； 引擎不复制。
为什么这样实现
引擎只有一份，所有仓库共用 —— 修一次就全部修好，不会出现五个仓库跑着 五个版本。代价是移动这个目录之后需要重装。
