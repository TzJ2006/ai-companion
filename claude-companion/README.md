# claude-companion

一个装进 Claude Code 的开发工作流。核心只有一句话：

> **项目里的每一个想法，都是图上的一个节点。想法 A 是想法 B 的前置，就有一条从 A
> 指向 B 的箭头。**

所有东西存在一个文件里：`ideas/graph.yaml`。没有第二份文档，没有四层结构，
没有阶段术语。不在这个文件里的东西，就是没有被追踪。

它解决的是三件事的同一个根因 —— AI 出幻觉、prompt 对不齐需求、返工之后自己也
看不懂项目框架：**想法从来没被写下来过，只有代码被写下来了。**

# 快速上手

## 1. 装进一个仓库

```bash
npx tsx D:/GitHub/ai-companion/claude-companion/install.ts <目标仓库路径>
```

会做三件事：把五个斜杠命令放进 `<目标仓库>/.claude/commands/`、建一个空的
`ideas/graph.yaml`、把守卫挂进 `.claude/settings.json`（不会覆盖已有的 hook）。

引擎本身**不复制** —— 所有仓库共用 `claude-companion/` 这一份，修一次全部修好。
装完**重启一下那个仓库的 Claude Code**，hook 才会生效。

## 装出去之后怎么更新

分两半，因为只有一半是拷贝：

| | 是不是拷贝 | 怎么更新 |
|---|---|---|
| 引擎（`ideas.ts` / `guard.ts` / `FORMAT.md`） | 否，所有仓库跑同一份 | **改完立刻生效**，什么都不用做 |
| 五个命令文件 | 是 | 要刷新 |

```bash
npx tsx claude-companion/install.ts --status   # 每个已装仓库是不是最新
npx tsx claude-companion/install.ts --update   # 全部刷新
```

装过的仓库记在 `claude-companion/.installs.json`（本机绝对路径，不进 git）。
「是不是最新」靠**和当前源文件逐字比对**，不是靠版本号 —— 版本号总有一天会忘记改，
内容自己知道对不对。四种状态：`current` / `stale` / `missing` / `foreign`
（`foreign` = 那个文件名被别人占了，`--update` 不碰它）。

比对前会先统一换行符。Windows 上 git 给你的源文件是 CRLF、装出去的是 LF，
不统一的话每个安装都会被永远报成过期，这个检查就废了。

`claude-companion/` 整个目录挪了位置也用 `--update` 修 —— 命令文件里烧的是绝对路径。

## 2. 第一次进一个项目

```
/ccscan
```

AI 通读整个项目，把它变成一张想法图，然后停下来给你看。

「通读」不是它说了算：`/ccscan` 开始时先把所有文件路径列成一张清单
（`ideas/.scan-todo`），**每 `Read` 一个文件就自动划掉一个** —— 由 hook 划，
不是它自己划。所以它报的是 `已读 487/511` 这种数字，而不是「我读完了」。
清单没清空，`check` 会一直警告。

跑完你会拿到 `ideas/graph.html`。**打开它。** 这是你唯一必须亲自做的事。

看三样东西：

- **有没有节点做了太多事** —— 一个节点应该是一件能独立做完、独立验证的事
- **有没有缺边** —— A 明明要先做，图上却没有 A → B 的箭头
- **有没有节点通向不了任何终点** —— 那要么是白做的，要么是终点漏写了

`/ccscan` 报告的最后一段会列出**它没能回答的问题**（哪些节点的 `why_this_way`
或 `verify` 是空的）。这段最有价值 —— 它诚实地告诉你哪里它也不知道，
而不是编一个理由糊过去。

## 3. 批准

看完觉得对，回一条消息，**内容就是两个字**：

```
批准
```

（`approve` / `同意` 也行，但必须是整条消息。「我不批准」不会被误判成批准。）

在你批准之前，AI **写不了任何一行实现代码** —— 守卫会拦下来。这不是提示词里的
约定，是 hook 层的硬拦截。

## 4. 开始做

```
/ccbuild
```

AI 按拓扑序推进：先写测试并确认它失败，再实现，再验证，通过才标完成。

# 五个命令

| 命令 | 干什么 | 你要做什么 |
|------|--------|-----------|
| `/ccscan` | 通读整个项目，建图，可视化 | 看图 → 回「批准」 |
| `/ccthink` | 新想法：对齐 → 拆分 → 调研 → 排期 | 答 3 个问题 → 看拆分 → 审计划 → 回「批准」 |
| `/ccbuild` | 按序实现：测试先行 | 基本不用管，失败时它会来问你 |
| `/ccfix` | 调试：先查一致性，再查想法 | 判断是代码错了还是想法错了 |
| `/ccgraph` | 看图、校验、说现在能做什么 | 随时问「我到哪了」 |

## `/ccthink` —— 有新想法的时候

这是最常用的一个。六步，AI 不能跳：

**第 1 步 · 对齐（你要答 3 个问题）**
AI 进 plan 模式，一次问一个，都是高层问题：

1. 要做什么？
2. 预期结果是什么？
3. 为什么要做这个？

然后它会用自己的话复述一遍。**如果复述错了，现在纠正是整个项目里最便宜的一刻。**

**第 2 步 · 拆分（你要看图）**
把大想法拆成小想法，渲染出来，停下来等你说这个拆法对不对。这时候每个节点只有
前三问，`how` 和 `why_this_way` 是空的 —— 因为还没调研，填了就是猜。

**第 3 步 · 调研（AI 做，你可以否决）**
两轮，都是强制的：仓库里已经有什么能复用；网上有没有人已经造过。

> **能借就借，是这个命令里优先级最高的规则。** 只要存在可用的东西 —— 一个库、
> 一个模式、一份踩坑记录 —— 计划就借它。自己造需要一个经得起追问的理由。
> 唯一的例外是你明确说了不许用某个项目。

**第 4-5 步 · 回答「如何实现」「为什么这样实现」，并设计测试**
测试只**设计**不**写**。写测试是 `/ccbuild` 的事，而且必须写在实现之前。

**第 6 步 · 完整计划（你要审）**
按周排期，拓扑序，每周能演示什么、哪几周是猜的。你回「批准」才能开工。

## `/ccfix` —— 出问题的时候

两步，顺序是方法的全部：

**第 1 步：代码和想法一致吗？**
对照每个 `code` 指的行，逐条比。**每一条不一致都带行号**：

```
ideas/graph.yaml  I-014.how    "缓存第一次命中的结果"
src/resolver.ts:41-53           没有缓存，每次都重新解析
→ 文档说要缓存，实现没有。
```

然后停下来问你：**是代码错了，还是想法过期了？** AI 判断不了这个 —— 这正是
这一步以人审收尾的原因。大部分 bug 到这里就结束了。

**第 2 步：想法本身错了**
只有第 1 步什么都没找到时才走。AI 会摆出**真实的**输入输出（不是举例值，
必要时插桩跑一遍再清掉），加上完整八问，让你看出是哪一问错了。然后你改想法。

---

# 八个问题

每个节点必答。这是整套东西的地基：

| # | | 什么时候答 |
|---|---|---|
| 1 | 这个想法是什么 | `/ccthink` 第 2 步 |
| 2 | 为什么有这个想法 | 同上 |
| 3 | 预期结果是什么 | 同上 |
| 4 | 要如何实现 | `/ccthink` 第 4 步（调研之后） |
| 5 | 为什么要这样实现 | 同上 |
| 6 | 代码在哪个文件的哪几行 | 计划时定文件，`/ccbuild` 填行号 |
| 7 | 实现后如何验证 | `/ccthink` 第 5 步 |
| 8 | 未来可以如何使用 | `/ccthink` 第 2 步 |

完整格式见 [FORMAT.md](FORMAT.md)。

# 被拦下来的时候

七条规则跑在 hook 层，agent 绕不过去。你也会撞上它们，所以先认识一下：

| 拦截信息 | 意思 | 你该做什么 |
|---|---|---|
| `这张想法图还没有人审核过` | R6：没批准 | 打开 `ideas/graph.html`，回「批准」 |
| `想法图在上次批准之后被改过了` | R6：批准失效了 | 图变了要重新过眼，再回「批准」 |
| `测试先行：xxx 的测试还不存在` | R3 | 让 AI 先写那个测试文件 |
| `xxx 还没想清楚就要动手` | R4：`how`/`why_this_way` 是空的 | 跑 `/ccthink` 把这个想法补完 |
| `不能手改已有想法的 status` | R2 | 用它给出的 `ideas.ts set` 命令 |
| `想法图有 N 个错误，修完再结束` | R5 | 按提示修，通常是 `done` 却没有 `code` |

另外两条不拦你，只是在背后记账：**R1** 每次 Edit/Write 自动写进 `ideas/log.md`；
**R7** 每次 `Read` 自动从扫描清单里划掉一个文件。

## R6 和 R7 为什么伪造不了

同一个思路：**把「我做了」绑到一个不真做就产生不了的事件上**。
agent 写得进去的标记，agent 就能伪造 —— 所以标记不能由它来写。

- **R6 靠 `UserPromptSubmit`** —— 只有你亲手敲消息才会触发，agent 没有任何工具能
  产生这个事件。批准绑定在图的 sha256 上，图改一个字就失效。
- **R7 靠 `Read`** —— 想把一个文件从扫描清单上划掉，就必须真的 Read 它，而 Read
  意味着内容确实进了它的上下文。「我读完了」于是变成一个倒计时，而不是一句保证。
  `Grep` / `Glob` 不算，它们不把文件内容放进上下文。
- 两者的账本文件（`.approved` / `.scan-todo`）本身也被 PreToolUse 拦住，
  不能用 Write 直接写 —— 否则「不可伪造」只是把伪造挪了个地方。

**已知天花板**：agent 仍然可以用 Bash 直接 `echo '{...}' | npx tsx guard.ts`
喂一个假的 UserPromptSubmit 事件，从而伪造批准。R6 挡住的是「顺手跳过」，
不是一个铁了心要绕过去的 agent。真要堵死，得让守卫能分辨自己是被 hook 系统
调用的还是被 Bash 调用的 —— 目前做不到，所以这里如实写出来，而不是假装它是密不透风的。

**卡住了**：`AIDEV_GUARD=off` 临时关掉全部七条。守卫的所有异常路径一律放行，
它自己崩了不会把你锁在外面。

# `ideas/` 里有什么

```
ideas/graph.yaml     ← 唯一需要编辑的文件（但状态要走 set）
ideas/graph.html     ← 生成的，别手改，会被覆盖
ideas/log.md         ← 自动追加，每次编辑一行，不需要 AI 配合
ideas/.approved      ← 你批准过的那一版图的哈希
ideas/.scan-todo     ← 扫描清单，读一个划一个；空了就是真读完了
```

**一个仓库里可能住着好几个 agent 的 companion。** Claude、Codex、Cursor 都想要
`ideas/graph.yaml`，谁后写谁就毁掉前一个。所以规则是**名字空着就用，被占了就加后缀**：

```
ideas/graph.yaml 空着  →  Claude 用它，并在文件里写上 agent: claude
ideas/graph.yaml 被占  →  Claude 用 ideas/graph.claude.yaml
                          配套文件一起加后缀：.approved.claude / .scan-todo.claude / log.claude.md
```

先到的保留干净名字，谁也不覆盖谁。选择做一次就固定 —— 因为「后缀文件存在」本身
就是答案。图里的 `agent:` 不是装饰，它是这张图声明归属的方式；一个没有 `agent:`
的 `graph.yaml` 会被当成别人的，因为反过来假设就会毁掉别人的东西。

# 引擎速查

平时用不上，是命令在背后调的。想自己看的时候：

```bash
C=D:/GitHub/ai-companion/claude-companion

npx tsx $C/ideas.ts check       # 校验，有错退出码 1
npx tsx $C/ideas.ts next        # 现在可以做哪些想法（前沿）
npx tsx $C/ideas.ts show I-014  # 一个想法：八问 + 前置 + 后继
npx tsx $C/ideas.ts render      # → ideas/graph.html
npx tsx $C/ideas.ts set I-014 done --by me --note "原因"
npx tsx $C/ideas.ts init        # 建一个空图
npx tsx $C/ideas.ts scan        # 扫描进度：已读 N/M，并列出还没读的
npx tsx $C/ideas.ts scan --reset --n 0   # 重建清单，打印全部
```

都接受 `--file <路径>`（默认 `ideas/graph.yaml`）和 `--project <目录>`（默认当前目录）。

`check` 拦的是让这套东西失效的几件事：

- `done` 却没有 `code` 或 `verify` —— 那个「完成」不成立
- `done` 的 `code` 指向不存在的文件 —— 记录已经和现实脱节
  （`todo` 的不查：那是计划中的位置，本来就还不该存在）
- 环 —— 那是两个想法应该合并
- 没有任何终点依赖的想法 —— 要么白做，要么终点漏了
- 人工验证（`verify.manual`）没有人签字就想标 `done`
- 扫描清单还没清空 —— 这张图是从半张项目上建起来的（警告，不拦）

# 例子

[`example/graph.yaml`](example/graph.yaml) 是这套工具描述它自己，13 个想法，
`check` 通过。渲染出来看：

```bash
npx tsx claude-companion/ideas.ts render --file claude-companion/example/graph.yaml
```

图上：上面是完整项目图**只显示想法名称**，每个节点可点，点进去是八问的全部回答，
加上**它的前置想法**和**它是哪些想法的前置**，两个方向都能继续点。
按状态着色：已完成 / 进行中 / 待办 / 受阻，终点单独高亮。

# 老实说

这套东西**还没有完整跑通过一次**。例子图里 `I-012「整条工作流跑通」` 是 `todo`，
那不是谦虚，是事实：引擎和守卫有测试（19 + 15 个用例），五个命令写完了但
还没在真项目上从头到尾走过一遍。

第一次用的时候，多半会发现某个命令的某一步写得不对。那时候的正确做法是跑
`/ccthink` 改它 —— 用它自己改它自己，这正是 I-012 想验证的事。
